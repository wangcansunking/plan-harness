# plan-full

Orchestrate the complete planning workflow end-to-end. This skill runs `/plan-init` once (if needed), then every `/plan-gen <type>` in topological order, with user checkpoints between phases, a fail-closed lint + validate + Validator-agent gates per doc, and the per-story mockup discipline applied throughout.

## When to Use

- User wants to generate ALL planning documents for a feature in one session.
- Triggers: "full plan", "plan everything", "complete planning", "plan-full", "generate all plans", `/plan-full`.
- Starting a brand-new feature that needs the complete planning treatment.

## What it produces

All files land under `plan-harness/<scenario>/`. Shared assets land under `plan-harness/_shared/`.

| File                                          | Generated by                  | Description                                                            |
|-----------------------------------------------|-------------------------------|------------------------------------------------------------------------|
| `manifest.json`                               | `/plan-init` (then updated)   | Scenario manifest — DAG state, meta-hashes, contexts                  |
| `_shared/context/overview.{html,meta.json}`   | `/plan-gen context` (once)    | Repo-level snapshot — modules, key files, entrypoints                  |
| `_shared/glossary/glossary.{html,meta.json}`  | `/plan-gen glossary` (once)   | Canonical terms                                                        |
| `_shared/decisions/*.{html,meta.json}`        | `/plan-gen decisions` (lazy)  | ADRs offered mid-grill when a decision crosses the 3-gate threshold    |
| `product.{html,meta.json}`                    | `/plan-gen product`           | DAG root — problem + users + userStories with REQUIRED per-story mockup |
| `analysis.{html,meta.json}`                   | `/plan-gen analysis`          | Pain points + root causes + ranked hypotheses                          |
| `design.{html,meta.json}`                     | `/plan-gen design`            | WHAT we build — REQUIRED mockup + flow on every design                 |
| `state-machine.{html,meta.json}`              | `/plan-gen state-machine`     | Lifecycle + corner cases + REQUIRED `perStoryFlows[]` per story        |
| `test-spec.{html,meta.json}`                  | `/plan-gen test-spec`         | Vertical slices + scenarios (replaces the old test-plan + test-cases) |
| `implementation.{html,meta.json}`             | `/plan-gen implementation`    | PR DAG, file tables, risks, HITL/AFK matrix                            |
| `test-report.{html,meta.json}`                | `/plan-gen test-report`       | Live E2E run + interactive fix loop                                    |

The dashboard at `http://localhost:<port>/scenario/<scenarioName>` indexes everything — no separate `dashboard.html` is generated.

## Prerequisites

- A repository to plan for (auto-detected from cwd or supplied via `--repo`).
- The plan-harness MCP server running (auto-started by `/plan-init` in Step 0).

## Workflow

The DAG is the authoritative ordering — see `prompts/_workflow.md`:

```
                    _shared/context ┐
                    _shared/glossary┤ (one-shot, soft inputs)
                    _shared/decisions ─ (added lazily mid-grill)
                                    ↓
product → analysis → design ┬─► state-machine ─┐
                             ├─► test-spec ◄────┤
                             └─► implementation ◄┤
                                      └─► test-report ◄─┘
```

Every per-doc generation follows the three-phase contract (`Phase A` draft → `Phase B` grill → `Phase C` render-with-lint-and-validate-gates) defined in `skills/plan-gen/SKILL.md`. plan-full does not bypass it. Both gates are fail-closed: `<doc>.lint.json` or `<doc>.validate.json` next to the HTML means the doc has NOT advanced and `<type>GeneratedAt` is NOT set.

### Phase 0 — Initialize

1. Check for `plan-harness/<scenario>/manifest.json` in this workspace.
   - If it exists: read it, print a one-line summary (`Scenario X · last gen Y · M/7 docs generated`), and ask `re-init [r] / continue [c] / abort [a]?`.
   - If missing: invoke `/plan-init`. That skill:
     - detects the repo, asks the user to select / create a scenario,
     - imports built-in contexts on first use,
     - writes `plan-harness/<scenario>/manifest.json`,
     - auto-starts the dashboard server and opens the browser.
2. After init, print:
   ```
   Scenario:   {scenarioName}
   Repository: {repoRoot}
   Dashboard:  http://localhost:{port}/scenario/{scenarioName}
   ```

### Phase 0.5 — Bootstrap shared assets (one-shot per workspace)

Shared assets live in `_shared/` and apply to every scenario. plan-full bootstraps them if missing — they're cheap and downstream docs cite them.

1. If `_shared/context/overview.meta.json` is missing → invoke `/plan-gen context`.
2. If `_shared/glossary/glossary.meta.json` is missing → invoke `/plan-gen glossary`.
3. ADRs (`_shared/decisions/`) are created lazily — Phase B grilling offers an ADR whenever a hard-to-reverse + surprising + real-trade-off decision surfaces.

Skip with `--no-shared` if the user knows the assets are current.

### Phase 1 — Gather feature description (drives `product`)

Ask the user to describe the feature. This becomes the seed for `product.meta.json`:

> Describe the feature or change you want to plan. Cover:
> - **What does it do?** (core functionality)
> - **Who is it for?** (target users + their need)
> - **What surface?** (UI screens / CLI commands / library API)
> - **Constraints?** (timeline, compatibility, security)
>
> Be detailed — this drives every downstream doc.

If the description is < 50 words, ask 1–2 targeted follow-ups (UI shape, data shape, external services). Persist the enriched description in `manifest.contexts.featureBrief`.

### Phase 2 — `/plan-gen product`

Invoke `/plan-gen product`. The skill itself runs Phase A → B → C with the lint + validate + Validator-agent gates. Key checkpoints plan-full surfaces:

- After Phase B, `product.userStories[]` is finalized. **Every story MUST have a `mockup` field** — terminal-output sketch for CLI, API-shape sketch for libraries, screen sketch for UI. plan-full does not advance until the user confirms each mockup form.
- After Phase C succeeds (lint clean), print:
  ```
  [1/7] product.html      generated  ({n} stories · {m} success metrics)
  ```

### Phase 3 — `/plan-gen analysis`

Invoke `/plan-gen analysis`. Hard upstream: `product`. Soft: `_shared/{context,glossary,decisions}`.

```
[2/7] analysis.html     generated  ({n} pain points · {m} root causes · {k} hypotheses)
```

**User-review checkpoint:** present the one-line problem framing, the top-3 pain points (with file:line citations), and the ranked hypotheses. Ask `accept [Enter] / re-grill <field> / re-run`. plan-full does not advance until the user accepts.

### Phase 4 — `/plan-gen design`

Invoke `/plan-gen design`. Hard upstream: `analysis`.

The skill enforces (via `L3-ux-visuals`): every design has a **mockup** AND a **flow/workflow** visual. Non-UI surfaces use terminal sketches / call-sequence diagrams. plan-full will NOT advance if Phase C lint fails — it surfaces the lint findings and re-grills.

```
[3/7] design.html       generated  ({n} decisions · {m} interfaces · {k} mockups)
```

**User-review checkpoint:** present `decisions[].tradeOff` (the rejected alternatives) + `interfaces[]` summary + mockup gallery thumbnails. Ask for accept / re-grill.

### Phase 5 — `/plan-gen state-machine`

Invoke `/plan-gen state-machine`. Hard upstream: `design` AND `product` (the latter feeds `perStoryFlows[]`).

The skill enforces (via `L3-story-flows`): one state-path visual per `product.userStories[]` entry. UI-bearing stories also get a `uiMockup` snapshot per key state.

```
[4/7] state-machine.html generated  ({n} machines · {m} states · {k} per-story flows · {l} corner cases)
```

### Phase 6 — `/plan-gen test-spec`

Invoke `/plan-gen test-spec`. Hard upstream: `design`. Soft: `state-machine`.

`test-spec` merges what used to be split across two docs into one: vertical slices (1:1 to PRs), Given/When/Then scenarios with priority labels, defect-repro entries seeded from `design.knownDefects[]`, HITL/AFK matrix.

```
[5/7] test-spec.html    generated  ({n} slices · P0:{p0} P1:{p1} P2:{p2} · {m} scenarios)
```

### Phase 7 — `/plan-gen implementation`

Invoke `/plan-gen implementation`. Hard upstream: `design`. Soft: `state-machine`, `test-spec`.

The most expensive type — dispatches the full agent team (Architect, PM, Frontend Dev, Backend Dev, Tester, Writer). `prs[]` is seeded 1:1 from `test-spec.verticalSlices`.

```
[6/7] implementation.html generated  ({n} PRs · DAG depth {d} · {m} HITL / {k} AFK)
```

### Phase 8 — `/plan-gen test-report`

Defer this phase until at least PR-1..PR-3 have landed — `test-report` runs Playwright against real `.test-evidence/`. plan-full does NOT block on it: print a clear "deferred" line and proceed to Phase 9.

If the user passes `--with-test-report` AND the manifest indicates `implementation.prs[].some(pr => pr.status === 'merged')`, then run it:

```
[7/7] test-report.html  generated  (P0:{green}/{total} green · {fixed} fixes applied during loop)
```

Otherwise:
```
[7/7] test-report.html  deferred   (run /plan-gen test-report after PR-1..PR-3 land)
```

### Phase 9 — Final summary + dashboard

No separate `dashboard.html` is written — the proxy serves `http://localhost:<port>/scenario/<scenarioName>` as the index, indexing every per-doc file. plan-full just prints the summary and opens that URL (via `plan_serve_dashboard` MCP tool if available).

```
=== plan-full complete ===

Scenario:     {scenarioName}
Repository:   {repoRoot}
Path:         plan-harness/{scenarioName}/
Duration:     {mm:ss}
Lint:         all docs clean (no <doc>.lint.json files remain)
Validate:     all docs clean (no <doc>.validate.json files remain)
Validator:    all docs accepted (no <doc>.validator.json files remain)

Generated:
  [✓] product.html
  [✓] analysis.html
  [✓] design.html
  [✓] state-machine.html
  [✓] test-spec.html
  [✓] implementation.html
  [○] test-report.html  (deferred — needs landed PRs)

Open dashboard:
  http://localhost:{port}/scenario/{scenarioName}              ← scenario index
  http://localhost:{port}/{scenarioName}/design.html           ← any individual doc
  http://localhost:{port}/_shared/glossary/glossary.html       ← shared assets

Next steps:
  /plan-edit <doc> <hint>       Single-doc field edit, no cascade
  /plan-sync                    Hash-based cascade if you edit any upstream
  /plan-gen test-report         Run end-to-end verification after PRs land
```

## Iterative feedback

At every user-review checkpoint (Phases 2, 3, 4):

1. User types feedback OR `re-grill <field>` OR presses Enter to accept.
2. On feedback: invoke `/plan-gen <doc> --cascade --field-allowlist <list>` so only the changed fields are re-asked — the rest of the meta is preserved.
3. After re-generation, show the updated summary and re-prompt.
4. On accept: advance to the next phase.

If the user says "redo everything" or "start over", drop back to Phase 1 with the updated description and re-run Phases 2+.

## Sub-commands

| Invocation                          | Behavior                                                                 |
|-------------------------------------|--------------------------------------------------------------------------|
| `/plan-full`                        | Auto-detect scenario; bootstrap shared assets; run product → implementation |
| `/plan-full <scenarioName>`         | Target a named scenario instead of auto-detecting                        |
| `/plan-full --with-test-report`     | Also run `/plan-gen test-report` after implementation (requires landed PRs) |
| `/plan-full --no-shared`            | Skip Phase 0.5 (assume `_shared/` already current)                       |
| `/plan-full --skip-product`         | Begin at analysis (only valid if `product.meta.json` already exists)     |
| `/plan-full --no-grill`             | Pass through to each `/plan-gen` — Phase A draft becomes final (quality lower) |

## Error handling

| Error                                                        | Resolution                                                                              |
|--------------------------------------------------------------|-----------------------------------------------------------------------------------------|
| `manifest.json` missing AND user declined re-init            | Stop: "Cannot run /plan-full without a scenario manifest."                              |
| MCP server fails to start                                    | Print error; fall back to direct file writes; warn that the dashboard won't be available |
| A `/plan-gen <type>` invocation fails Phase C lint           | Surface `<doc>.lint.json`; offer `[r]e-grill / [s]kip / [a]bort`; never silently advance |
| A `/plan-gen <type>` invocation fails Phase C validate       | Surface `<doc>.validate.json`; offer `[r]e-grill <field> / [s]kip / [a]bort`. Validate runs after lint; both must be clean for the doc to advance. |
| User abandons mid-workflow                                   | Every doc generated up to that point remains valid + linked from the dashboard          |
| `/plan-gen state-machine` fires `L3-story-flows` because `perStoryFlows.length !== userStories.length` | Re-grill perStoryFlows[]; never proceed with mismatched count                          |
| `/plan-gen design` fires `L3-ux-visuals`                     | Re-grill mockup/flow coverage; advance only when both visuals are present              |

## Principles

1. **Topological, never batched.** Each `/plan-gen <doc>` reads the freshly-finalized upstream meta — no parallelism between dependent docs.
2. **Lint, validate, AND Validator-agent verdict are the gates, not suggestions.** A doc with a `<doc>.lint.json` / `<doc>.validate.json` / `<doc>.validator.json` next to it has NOT advanced — plan-full will not pretend it did. Lint catches HTML structure; validate catches schema + cross-doc refs + HTML semantic coverage; the Validator agent catches the human-style audit (contract coverage, mockup rigor, glossary/ADR hygiene, caveman readability). All three must be clean.
3. **Mockups are first-class everywhere.** product → per-story; design → mockup + flow; state-machine → per-story flow + per-state UI snapshot when UI applies.
4. **Checkpoints are interactive only on the upstream three** (product, analysis, design). state-machine / test-spec / implementation print a brief confirmation; their content is mechanically derived from upstream meta + repo reads.
5. **Single source for the workflow.** This skill cites `prompts/_workflow.md`; if the DAG changes, update that file first.
